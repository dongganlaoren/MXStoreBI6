### 财务报销模块设计 V2.0 (最终版)

#### **1. 模块目标 (Module Goal)**

实现一个无纸化、流程清晰的在线财务报销申请与审批系统。MVP（最小可行产品）阶段的核心目标是打通“员工提交 -> 管理层审批”的核心闭环，并确保所有操作都有记录可循。

#### **2. 核心功能 (Core Features)**

* **报销申请创建**: 用户填写报销表单，上传必要的附件，并选择指定的审批人后提交。
* **报销申请审批**: 审批人审查申请详情及附件，填写审批意见（可选），并给出“通过”决定。
* **列表与查看**: 相关人员可以查看报销申请的列表和详细信息。

#### **3. 数据库设计 (Database Design)**

##### **3.1. 枚举类型 (Enumerations)**

为了提高代码的健壮性和可读性，模块中所有分类和状态均采用枚举类型。这些枚举统一定义在 `app/models/enums.py` 文件中。

* **`ReimbursementStatus`**: 报销申请的审批状态。
    * `PENDING`: 'PENDING' (待审批)
    * `APPROVED`: 'APPROVED' (已通过)
* **`ReimbursementPrimaryCategory`**: 成本一级分类。
    * `SHARED_COST`: "公摊成本"
    * `STORE_COST`: "店铺成本"
* **`ReimbursementSecondaryCategory`**: 成本二级分类。
    * 包含“公摊报销”、“代理记账”...“其它成本”等所有二级分类。
* **`ReimbursementAttachmentType`**: 报销流程附件类型。
    * `SUBMISSION`: "SUBMISSION" (提交阶段附件)
    * `APPROVAL`: "APPROVAL" (审批阶段附件)

#### **4. 核心业务流程 (Core Business Workflow)**

1.  **创建申请**:
    * 用户在前端页面填写表单。
    * 系统自动填充 `submitter_id` 为当前登录用户ID。
    * 用户提交后，在数据库创建一条 `reimbursement_requests` 记录，`status` 默认为 `PENDING`。
    * 所有上传的附件都在 `reimbursement_attachments` 表中创建记录，`attachment_type` 为 `SUBMISSION`。
2.  **审批申请**:
    * 角色为 "ADMIN" 或 "FINANCE" 的用户可以看到 `status` 为 `PENDING` 的申请列表。
    * 审批人打开详情页，审查信息。
    * 审批人可以填写 `approval_comments`（可选）和上传附件（可选）。
    * 审批人点击“通过”按钮后，系统将对应记录的 `status` 更新为 `APPROVED`，并记录 `approved_at` 时间。
    * (MVP版本不包含“驳回”流程)

#### **5. 字段校验规则 (Field Validation Rules)**

| 字段                     | 校验规则                                                     |
| :----------------------- | :----------------------------------------------------------- |
| **`primary_category`**   | **必填**；值必须是 `ReimbursementPrimaryCategory` 枚举之一。 |
| **`secondary_category`** | **必填**；值必须属于所选一级分类对应的二级分类枚举列表。     |
| **`store_id`**           | **条件必填**：当一级分类为“店铺成本”时**必填**；当为“公摊成本”时，该项禁用且值为`NULL`。 |
| **`reason`**             | **必填**；最大长度 500 字符。                                |
| **`submission_date`**    | **必填**；必须是有效的日期格式。                             |
| **`amount`**             | **必填**；必须是大于0的数字；最多2位小数。                   |
| **`currency`**           | **必填**；值必须是 'THB' 或 'CNY' 之一，前端默认为 'THB'。   |
| **`approver_id`**        | **必填**；必须从角色为 'ADMIN' 或 'FINANCE' 的用户列表中选择。 |
| **报销附件**             | **可选**；文件数量最多30个；单个文件大小上限 500MB；文件类型限制为常见的图片、文档和压缩包格式。 |
| **`approval_comments`**  | **可选**；最大长度 500 字符。                                |
| **审批附件**             | **可选**；规则同“报销附件”。                                 |
| **`submitter_id`**       | **系统生成**，无需校验。                                     |

#### **6. 关键设计决策 (Key Design Decisions)**

* **条件字段处理**: 对于 `store_id` 的条件必填逻辑，我们决定采用在同一张表中通过应用层逻辑进行控制的方案，以保证MVP阶段的开发简洁性和效率。
* **模块解耦**: 模块中用到的所有枚举（如状态、分类等）均为本模块专属或从通用枚举扩展而来，不与现有其他模块的枚举直接共用（或重命名），以确保未来各模块可独立演进，互不影响。
* **未来范围**: “抄送人”等功能被明确为非MVP功能，计划在后续版本中迭代。
