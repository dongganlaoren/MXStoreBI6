## 1. 项目背景与目标

### 1.1 背景

财务侧存在银行流水 PDF 解析与落库的自动化需求。当前需要支持多家银行流水格式，并且在入库前必须进行严格的自洽性校验，避免错误数据污染数据库。

### 1.2 目标

- **核心目标**：自动解析 **曼谷银行（BBL）** 与 **开泰银行（K-Bank）** 的交易流水 PDF；在通过严格的逻辑自洽性校验后，实现结构化数据
  **去重入库**。
- **应用群体**：财务人员、银行客户、金融应用开发者。

---

## 2. 业务流程与逻辑规范

> 目标：确保“上传 → 解析 → 校验 → 展示结果 → 落库”的流程可控、可追溯、可解释。

### 2.1 文件处理与查重

#### 2.1.1 哈希校验（防止重复导入）

- 上传时计算文件哈希值（如 **MD5**）。
- **禁止**相同文件重复导入。

#### 2.1.2 密码处理（PDF 加密场景）

- 若 PDF 加密：
    - 系统需先**自动尝试**使用服务端环境变量 `.env` 中的默认密码列表进行解密：
        - `BANK_STATEMENT_PASSWORD=15041990,12091988,28071997`
        - 解析策略：按逗号分隔，依次尝试（trim 空格），直到解密成功或列表耗尽。
    - 若默认密码全部失败：
        - 前端弹出/展示“请输入 PDF 密码”的输入框；
        - 用户输入后可再次提交解密请求。

- 安全要求：
    - 后端仅在**内存**中使用密码进行解析；
    - **严禁持久化存储**密码（包括数据库、日志、文件系统等）；
    - 日志中不得输出明文密码。

### 2.2 概况数据提取逻辑

#### 2.2.1 概况所在位置

- **开泰银行（K-Bank）**：概况位于文件**首页顶部**。
- **曼谷银行（BBL）**：概况位于文件**最后一页底部汇总表格**。

#### 2.2.2 必须提取的指标

必须包含以下 6 类指标：

- 期初金额
- 期末金额
- 进账总笔数
- 进账总金额
- 出账总笔数
- 出账总金额

### 2.3 交易明细特殊处理（首行过滤）

> 原则：某些“首行余额提示”仅用于校验，不应进入交易明细表。

- **开泰银行（K-Bank）**：
    - 每页首行 `Descriptions` 为 **"Beginning Balance"** 时：
        - 仅作为该页余额校验基准
        - **不作为**交易明细

- **曼谷银行（BBL）**：
    - 第一页首行 **"B/F"**：
        - 仅作为总期初基准
        - **不作为**交易明细

## 3. 三层核心自洽性校验

系统必须在展示预览前自动执行以下校验。仅当校验 **100% 正确** 时，才允许入库。

| 校验层级 | 校验项    | 数学公式                                        | 说明                  |
|------|--------|---------------------------------------------|---------------------|
| 第一层  | 汇总逻辑校验 | ∑明细进账 = 概况进账总额；∑明细出账 = 概况出账总额；明细总行数 = 概况总笔数 | 对“概况 vs 明细”的总量一致性校验 |
| 第二层  | 余额连续性  | 前一笔交易余额 + 当前进账 − 当前出账 = 当前交易余额              | 对“逐笔余额”连续性校验        |
| 第三层  | 期初期末校验 | 总期初金额 + 累计进账 − 累计出账 = 总期末金额                 | 对“整体期初/期末”闭环校验      |

## 4. 页面交互设计

> 说明：不提供“PDF 页面预览”能力（避免浏览器侧渲染差异与性能问题）；但必须提供**原始 PDF 下载**，以便人工核对。

### 4.1 页面信息结构（展示内容要求）

页面需要清晰展示三类信息，并保持整洁美观（符合现有 Bootstrap 风格）：

1. **文件信息卡片（File Card）**
    - 文件名、银行类型（BBL / K-Bank）、解析时间
    - 文件哈希（可折叠展示）
    - 原始 PDF 下载按钮（始终可见）

2. **概况数据卡片（Summary Card，必须展示）**

> 把从 PDF 中提取到的概况数据直接展示到页面上，便于财务快速核对。

- 期初金额
- 期末金额
- 进账总笔数 / 进账总金额
- 出账总笔数 / 出账总金额

展示建议（不限制实现，但需美观）：

- 使用 2×3 或 3×2 的指标格（Bootstrap `row` + `col`），数字右对齐；
- 金额统一格式（千分位、两位小数），并标注币种（如 THB，若可识别）。

3. **校验结果卡片（Validation Card，必须展示）**

> 将“三层核心自洽性校验”的结果展示在页面上，帮助定位失败原因。

- 总体状态：
    - 通过：绿色 Badge（例如 `PASS` / “校验通过”）
    - 失败：红色 Badge（例如 `FAIL` / “校验失败”）

- 分层展示（建议表格/列表形式）：
    - 第一层：汇总逻辑校验（显示：期望值、实际值、差值）
    - 第二层：余额连续性（显示：首次出现不一致的行号/时间、计算式与差值；可折叠查看更多）
    - 第三层：期初期末校验（显示：期望期末、实际期末、差值）

- 失败时的可读性要求：
    - 优先展示“最关键的 1~3 条差异”（摘要），其余放入可折叠区域；
    - 差异数字使用等宽字体或右对齐，避免视觉跳动。

### 4.2 交互流程（符合当前框架习惯）

#### 4.2.1 上传页（入口页）

- 组件：
    - 上传表单（`<input type="file">` + 提交按钮），支持拖拽可选
    - 可选：银行类型选择（若系统不能自动识别）

- 提交后的交互：
    - 上传成功后跳转到“解析结果页”（PRG 模式：Post/Redirect/Get），避免刷新重复提交。

#### 4.2.2 解析结果页

- 默认行为：
    - 展示“文件信息卡片 + 概况数据卡片 + 校验结果卡片”。

- PDF 加密且默认密码失败时：
    - 在解析结果页顶部展示一个明显但不突兀的警告提示（Bootstrap `alert-warning`）：
        - 文案示例：`PDF 已加密，系统默认密码尝试失败，请输入密码后重试解析。`
    - 同页提供密码输入框 + “重试解析”按钮。

- 下载能力：
    - 仅提供“下载原始 PDF”
    - 不提供 PDF 预览、也不提供逐页渲染。

#### 4.2.3 落库操作（确认入库）

- 仅当三层校验全部通过时，展示“确认落库”主按钮（Primary）。
- 若校验失败：
    - “确认落库”按钮禁用，并给出原因提示。

- 点击确认落库后：
    - 服务端执行去重入库（见 [4.2 入库与安全](#42-入库与安全)）
    - 成功后在页面顶部提示成功，并将该批次状态标记为只读（不可再次操作）。

### 4.3 入库与安全

#### 4.3.1 唯一性检查（明细去重）

- 落库时根据以下字段进行复合查重：
    - `日期 + 时间 + 金额 + 余额`
- 已存在的记录自动过滤。

#### 4.3.2 状态锁定（只读）

- 点击 **“确认落库”** 后：
    - 数据存入数据库
    - 设置为**只读状态**
    - 禁止编辑

## 5. 开发标准化要求（面向实现与 AI 协作）

> 本章节用于约束实现落地方式，确保代码与现有项目框架一致，并且对自动化/AI 辅助开发更友好。

### 5.1 框架一致性（必须遵循当前项目习惯）

- **后端**：遵循现有 Flask 工程结构与注册方式（Blueprint/路由/服务层/模型层），不得引入与现有结构冲突的“另起炉灶式”目录。
- **日志**：统一使用 `app.logger`，日志内容包含：文件哈希、银行类型、解析阶段、校验结果摘要；不得打印明文密码。
- **配置**：加密 PDF 默认密码从 `.env` 读取 `BANK_STATEMENT_PASSWORD`，不允许写死在代码里。
- **前端**：沿用现有 Bootstrap 页面风格与表单校验方式（提示、alert、badge、card 等组件），保证页面简洁、信息密度合理。
- **无 PDF 预览**：页面只提供原始 PDF 下载链接/按钮，不做嵌入式预览。

### 5.2 文件命名规范（必须以模块简称开头）

> 目的：让代码与文件在 IDE/仓库里按模块快速聚类，方便阅读、检索、批量改动。

- 成本治理模块简称：**`cg_`**（Cost Governance）。
- 新增文件命名必须符合：`cg_<功能>_<层>.py/.html/.js/.css`（按实际使用语言选用）。

示例（仅示例，具体以现有目录结构落位）：

- `app/services/cg_bank_statement_service.py`
- `app/views/cg_bank_statement_views.py`
- `app/templates/cg_bank_statement_result.html`
- `app/forms/cg_bank_statement_forms.py`

### 5.3 对 AI/自动化开发友好的交付提示语（实现时请严格按此输出）

为降低沟通成本、提升一次性成功率，要求开发过程中的交付信息遵循以下格式：

- **每一步先给“契约”**（2~4 行）：
    - 输入是什么（文件/参数）
    - 输出是什么（数据结构/页面渲染/入库结果）
    - 失败返回什么（错误码/错误信息/提示文案）

- **每次改动必须包含**：
    1. 修改了哪些文件（路径列表）
    2. 为什么这么改（对应 PRD 条目编号，如 2.1.2 / 4.1 / 4.2）
    3. 如何本地验证（最少 1 条可复制命令，例如 `pytest -k ...`）

- **避免不确定表述**：
    - 不写“可能/大概/应该没问题”，而是给出可验证的结论与证据（测试输出/截图说明/日志摘要）。

- **边界与异常场景必须显式列出并覆盖**（至少包含）：
    - PDF 未加密 / 已加密且默认密码成功 / 已加密且默认密码失败（需要用户输入）
    - 哈希命中重复文件
    - 概况缺失字段
    - 三层校验任意一层失败时页面展示与禁止入库

### 5.4 解析核心提取正则（K-Bank / BBL 样例）

> 本节用于固化“从 PDF 文本中提取概况与明细”的关键正则，便于后续维护与回归测试。
>
> 注意：三层核心自洽性校验（第 3 章）的数学公式保持不变，本节仅描述“数据怎么从 PDF 文本中提取出来”。

#### 5.4.1 通用金额 Token

- 金额 Token（支持千分位与两位小数）：

`-?\d{1,3}(?:,\d{3})*(?:\.\d{1,2})?`

#### 5.4.2 K-Bank（KASIKORNBANK）

**概况提取**（出现在首页/全局文本中）：

- 期初余额（Beginning Balance）：

`\bBeginning Balance\s+(?P<amt>{AMT})\b`

- 出账汇总（Total Withdrawal）：

`\bTotal Withdrawal\s+(?P<count>\d+)\s+Items\s+(?P<amt>{AMT})\b`

- 进账汇总（Total Deposit）：

`\bTotal Deposit\s+(?P<count>\d+)\s+Items\s+(?P<amt>{AMT})\b`

- 期末余额（Ending Balance，若存在则优先，否则取最后一笔余额）：

`\bEnding Balance\s+(?P<amt>{AMT})\b`

**明细行提取**（每行一笔，首行 Beginning Balance 需过滤不计入明细）：

```regex
^(?P<date>\d{2}-\d{2}-\d{2})\s+
(?:(?P<time>\d{2}:\d{2})\s+)?
(?P<desc>.+?)\s+
(?P<direction>Deposit|Withdrawal)\s+
(?P<amt>{AMT})\s+
(?P<bal>{AMT})\s*(?P<tail>.*)$
```

过滤规则（不计入交易明细）：

- `desc` 包含 `Beginning Balance` 的行。

#### 5.4.3 BBL（Bangkok Bank）

**概况提取**（位于最后一页底部汇总区域）：

- 出账汇总（Total Debits）：

`Total\s+No\.\s+of\s+Debits\s+(?P<count>\d+)\s+.*?Total\s+Debit\s+Amount\s+(?P<amt>{AMT})`

- 进账汇总（Total Credits）：

`Total\s+No\.\s+of\s+Credits\s+(?P<count>\d+)\s+.*?Total\s+Credit\s+Amount\s+(?P<amt>{AMT})`

**明细行提取**（每行一笔）：

`^(?P<date>\d{2}/\d{2}/\d{2})\s+(?P<desc>.+?)\s+(?P<amt>{AMT})\s+(?P<bal>{AMT})\s*(?P<tail>.*)$`

补充说明：

- BBL 明细的进/出账方向有时不直接给出，本实现使用“关键词启发式”进行判定（如 `TRF` 等视为进账，否则视为出账）；如需 100%
  精准，建议以银行字段列或版式坐标进一步增强。

> 使用时请把 `{AMT}` 替换为通用金额 Token 正则。
